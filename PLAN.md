# PSTATS Viewer — build plan

A local Next.js + Tailwind app that reads the JSON files PSTATS writes and
turns them into something worth looking at after a session.

Everything runs on your machine. No auth, no database, no deploy.

---

## 1. The data you're building against

Three real sample files are in `samples/`, generated by the tracker's own
serializer so the schema is exact:

| File | Contents |
|---|---|
| `2026-09-12_1747-0002_c1_coop.json` | Dead Center, Hard, 4 humans, 4 chapters, finale win |
| `2026-09-12_1747-0003_c2_coop.json` | Dark Carnival, Expert, 5 chapters, one wipe + retry, a player leaves mid-campaign and a bot takes over, finale win |
| `_current.json` | The Parish, Normal, solo with 3 bots, 2 chapters, still in progress |

These deliberately cover the awkward cases: a campaign in progress, a bot
takeover mid-campaign, a chapter played twice, a mix of humans and bots, and
the same four Steam IDs recurring across files so cross-campaign aggregation
is testable.

### Shape

```
{
  schema: 1,
  session_id: "2026-09-12_1747-0002",
  started_utc, updated_utc,          // unix seconds, may be 0
  campaign: "c1",                    // or a custom map name
  gamemode: "coop",
  difficulty: "Hard",                // Easy | Normal | Hard | Impossible
  playtime_s, round_starts, saves,
  outcomes: { finale_win: 1, map_cleared: 3, wipe: 1 },
  chapters: [ Chapter, ... ],        // in play order
  totals:   { <playerKey>: Player },  // chapters summed, regenerated on save
  events_seen: { player_death: 41, ... }
}

Chapter {
  map: "c1m2_streets", index: 2, started_utc,
  playtime_s, round_starts,
  outcome: "cleared" | "wipe" | "finale_win" | "in_progress",
  players: { <playerKey>: Player }
}

Player {
  name, steamid, character, is_bot, playtime_s,
  offense: {
    shots_fired, reloads, total_kills, witch_oneshots,
    ff_damage, ff_incaps, ff_kills,
    kills:        { common, smoker, boomer, hunter, spitter, jockey, charger, tank, witch, ... },
    headshots:    { <same keys> },
    damage_dealt: { <same keys> }
  },
  defense: {
    deaths, incaps, times_revived, times_defibbed, heals_taken, fall_damage,
    damage_taken: { hunter, common, fire, fall, teammate, tank, spitter_acid, explosion, world, ... },
    incapped_by:  { <source>: count },
    killed_by:    { <source>: count },
    grabbed_by:   { smoker, hunter, jockey, charger, boomer_vomit, hunter_escaped, ... }
  },
  teamwork: {
    revives_given, heals_given, pills_given, defibs_used, rescues, saves,
    pairs: { <otherPlayerKey>: {
      ff_damage_to, ff_damage_from, revived, revived_by,
      healed, healed_by, saved, saved_by, shoved, incapped, killed
    }}
  },
  actions: {
    shoves, jumps, pickups, car_alarms, witches_startled, panic_events,
    gun_overheats, props_broken, gascans_poured, tank_rocks_hit_by,
    items_used: { pipe_bomb, molotov, vomitjar, pain_pills, adrenaline, defibrillator }
  }
}
```

### Six things that will bite you

1. **Every sub-table is open-ended.** `kills`, `damage_taken`, `grabbed_by`
   etc. are built by key as events fire, so a key is absent when it never
   happened — and unexpected keys (`common_by_explosion`, a raw classname,
   `unknown`) can appear. Treat them as `Record<string, number>` and never
   index a fixed list. Parse with a permissive schema (`z.record(z.number())`),
   not an enum.
2. **`playerKey` is not always a Steam ID.** It's `STEAM_...` for humans,
   `BOT:Coach` for bots, and `NAME:whatever` when ID lookup failed. Key all
   state off this string; use `name`/`character` only for display.
3. **`totals` is derived, not authoritative-in-isolation.** It equals the sum
   of `chapters`. Read it for campaign views, but compute chapter views from
   `chapters` directly. Never sum `totals` across chapters again.
4. **`_current.json` may duplicate an archive.** If a `session_id` appears in
   more than one file, keep the copy with the higher `saves` (tiebreak on
   `updated_utc`) and drop the rest. Otherwise a finished campaign gets
   double-counted in all-time stats.
5. **`started_utc` can be `0`** on builds without a wall clock. Fall back to
   ordering by `session_id`, which sorts lexicographically into chronological
   order.
6. **A chapter can have `outcome: "in_progress"`** and a campaign can have no
   `finale_win`. Don't assume a campaign is complete.

## 2. Stack

- Next.js (App Router) + TypeScript
- Tailwind v4
- `zod` for parsing — non-negotiable, the data is best-effort and a bad file
  should produce a readable error, not a white screen
- `recharts` for the two or three real charts; plain SVG/CSS for bars and the
  heatmap (lighter and easier to style than forcing a chart lib into them)
- No state library. URL params + React state is enough.
- No database. No API routes beyond the one file-system loader below.

## 3. Getting data in — do both

**Dev loader (primary).** A server component reads `PSTATS_DIR` from
`.env.local`, defaulting to `./data`. You symlink your game folder once:

```bash
ln -s "/path/to/Left 4 Dead 2/left4dead2/ems/pstats" ./data
```

Then the app just shows current data on refresh, no uploading.

**Drag-and-drop (fallback).** A dropzone that accepts multiple `.json` files,
parses client-side, and keeps them in `localStorage`. Needed for viewing files
from a friend's machine, and for the deployed-nowhere case.

Both paths feed the same normalized store, so nothing downstream knows or
cares which was used.

## 4. Routes

| Route | Purpose |
|---|---|
| `/` | All-time overview across every loaded file |
| `/campaigns` | Campaign list, newest first |
| `/campaigns/[sessionId]` | One campaign; chapter tabs plus campaign totals |
| `/players/[playerKey]` | One player across all campaigns |
| `/friendly-fire` | The pair matrix, all-time and per-campaign |

## 5. What goes on each page

**`/` — overview.** Total playtime, campaigns played, win rate, all-time
kills. A per-player leaderboard (sortable, bots toggleable). A chart of kills
per minute by campaign over time so you can see whether you're improving.
Recent campaigns list with outcome badges.

**`/campaigns/[sessionId]`.** Header: campaign name, difficulty, gamemode,
duration, outcome, roster. Chapter tabs along the top — each tab shows that
chapter's per-player table, what killed and incapped people, and chapter
duration. A "campaign totals" tab. Difficulty and wipes should be visually
obvious; an Expert run with three wipes should not look like a Normal
walkthrough.

**`/players/[playerKey]`.** Headline stats: kills, K/min, headshot %, deaths,
incaps, revive ratio. Kill breakdown by infected type (horizontal bars —
common dwarfs everything, so give specials their own scale or split the
charts). Threat profile: which special infected actually hurts this player
most, from `damage_taken` + `grabbed_by` + `incapped_by`. A per-campaign trend
line.

**`/friendly-fire`.** The fun one. `teamwork.pairs` is directional, so render
an N×N heatmap: rows shot, columns got shot. Include a plain-language summary
line ("marco_ph has put 412 damage into jaytee across 3 campaigns; jaytee has
returned 38"). Pairs only exist where an interaction happened, so render
missing cells as zero-but-empty, not as gaps.

### Derived metrics to compute in a `lib/metrics.ts`

Kills per minute · headshot rate (`headshots` total / `kills` total, per type
too) · kills per shot as a rough accuracy proxy · FF damage per hour · incaps
per chapter · revive ratio (`revives_given` / `times_revived`) · deaths per
campaign · most dangerous special per player · survival rate (chapters cleared
without going down). Keep all of these in one module with unit tests; every
page reads from there rather than doing arithmetic in JSX.

## 6. Visual direction

Minimalist and modern, and specifically *not* a gamer-RGB dashboard.

- Dark, near-black background (`#0a0a0b`-ish), one accent colour, plenty of
  negative space. Data-ink over decoration: no gradients, no glass, no glow.
- One sans for UI (Geist or Inter). **Tabular numerals everywhere numbers
  align** — `font-variant-numeric: tabular-nums`. This single detail does more
  for the "modern dashboard" feel than any amount of styling.
- Tight, deliberate type scale. Big numbers for headline stats, small caps or
  muted labels beneath.
- Semantic colour, used sparingly: one accent for the user's own stats, a warm
  tone reserved for friendly fire and deaths, neutral grey for everything else.
  Never colour-code by player identity alone — four-player palettes get
  muddy — use position plus label.
- Infected types get consistent iconography or a consistent colour slot across
  every chart, so "hunter" is always the same thing visually.
- Tables: no vertical rules, minimal horizontal rules, generous row padding,
  hover row highlight, right-aligned numbers.
- Responsive but desktop-first. You'll read this on the machine you play on.
- Empty and error states designed, not an afterthought: no files loaded, a
  file that fails schema validation, a campaign with one chapter, a player
  with zero kills.

## 7. Build order

1. **Data layer.** Zod schema, fs loader, dropzone, normalization, dedupe by
   `session_id`. Prove it by rendering an ugly `<pre>` of parsed output for all
   three sample files. Don't style anything yet.
2. **Metrics module** with tests against the samples. The numbers being right
   matters more than the layout.
3. **Campaign detail page** — the most useful view, and it forces the chapter
   tab pattern and the shared player-table component.
4. **Overview page** reusing those components.
5. **Player profile** and **friendly-fire matrix**.
6. **Design pass.** Typography, spacing, empty states, transitions. Do this as
   a deliberate pass rather than while wiring data.

## 8. Testing

Point Vitest at the three sample files as fixtures. Worth asserting:

- All three parse without error
- `totals` equals the sum of `chapters` for every player in every file
- Dedupe keeps one copy when `_current.json` and an archive share a `session_id`
- A file with unknown keys in `kills` still parses
- Bot and human keys are distinguished correctly
- The c2 sample's departed player shows less playtime than the others

## 9. Out of scope

Live updating while the game runs, a server deploy, editing the JSON, and any
kind of accounts. If live refresh becomes tempting later, poll the fs loader
on an interval rather than adding websockets.
